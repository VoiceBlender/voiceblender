# VoiceBlender - Claude Code Instructions

## After every code change

1. **Format Go code** — Run `gofmt` on all changed files.

2. **Regenerate OpenAPI spec** — If any REST API endpoints, request/response schemas, or configuration environment variables changed, update the Go source types/route metadata and run `make openapi` to regenerate `openapi.yaml`. Never hand-edit `openapi.yaml` directly — it is generated by `go generate ./internal/api/` (see `cmd/openapi-gen/`) and manual edits will be overwritten.

3. **Regenerate AsyncAPI spec** — If any VSI command (added, removed, renamed, payload changed) or any event in `internal/events` changed, update `internal/api/vsi_meta.go` (the `VSICommandsMetadata`, `EventsMetadata`, or `VSILifecycleFramesMetadata` registries) and run `make asyncapi` to regenerate `asyncapi.yaml`. Every VSI command and every event MUST appear in the registries — if it isn't there, it isn't in the spec. Never hand-edit `asyncapi.yaml` directly — it is generated by `cmd/asyncapi-gen/` and manual edits will be overwritten. Use `make specs` to regenerate both `openapi.yaml` and `asyncapi.yaml` in one shot.

4. **Update API documentation** — If any REST API endpoints, request bodies, response schemas, or webhook events changed, update `API.md`. Include usage examples.

5. **Update README.md** — If new configuration environment variables or features were added, update the relevant tables/sections in `README.md`.

6. **Update `voiceblender.env.example`** — If any environment variable was added, removed, renamed, or had its default changed in `internal/config/config.go`, update `voiceblender.env.example` in the repo root to match. Every env var the server reads must appear in the example file with its real default value; secrets/empty defaults are shown as empty assignments. The example file is committed; the actual `voiceblender.env` is not.

7. **Unit tests** — Every new feature, package, or extension to an existing package must have unit tests.

8. **Integration tests** — Every new or updated feature must have integration tests in `tests/integration/`.

9. **Update TESTING.md** — If new test commands, test files, test data setup steps, or testing workflows were added, update `TESTING.md` with the relevant instructions and test list entries.

10. **Do not change API unless required** - We should keep API unchanged as much as possible to keep backwards compatibility. 

## Git commits

Never run `git commit` (or any other git operation that creates a commit, including `git commit --amend`, `git merge --no-ff`, `git rebase`, etc.). Stage changes and leave the commit to the user. This applies even when work is finished and "ready to commit" — stop at staging.

## Code comments

Keep code comments minimal. Default to no comment. Only add one when the **why** is non-obvious — a hidden constraint, a subtle invariant, a workaround for a specific bug, behaviour that would surprise a reader. One short line is almost always enough; never write multi-paragraph rationale, narrative, or war-story comments inline. Don't restate what well-named code already shows. Don't reference specific vendor implementations, past incidents, ticket numbers, or "we used to do X, now we do Y" in source — that belongs in commit messages or PR descriptions.
