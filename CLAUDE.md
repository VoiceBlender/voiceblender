# VoiceBlender - Claude Code Instructions

## After every code change

1. **Format Go code** — Run `gofmt` on all changed files.

2. **Regenerate OpenAPI spec** — If any REST API endpoints, request/response schemas, or configuration environment variables changed, update the Go source types/route metadata and run `make openapi` to regenerate `openapi.yaml`. Never hand-edit `openapi.yaml` directly — it is generated by `go generate ./internal/api/` (see `cmd/openapi-gen/`) and manual edits will be overwritten.

3. **Register every route with the OpenAPI generator** — The generator does **not** discover routes. It only reads `RoutesMetadata()` in `internal/api/openapi_meta.go`. A handler wired into chi in `internal/api/server.go` but missing from `RoutesMetadata()` produces no spec entry, no warning, and a clean `make openapi` run — the endpoint silently disappears from the docs. Whenever a route is added, removed, renamed, or has its method, path, request body, response codes, or tags changed in `internal/api/server.go`:
   - Add or update the matching `RouteMeta` entry in `RoutesMetadata()` — method, path, `OperationID`, summary, tags, request type, and **every** response code the handler can return.
   - If the route introduces a new tag, add it to `tagDescriptions()` in `cmd/openapi-gen/main.go`; generation fails hard otherwise.
   - Run `make specs`, then verify the endpoint is really in the output (`grep` the new path in `openapi.yaml`). An unchanged `openapi.yaml` after an API change means the metadata was not updated — it never means there was nothing to do.
   - Cross-check both lists before finishing: every `r.Get/Post/Put/Patch/Delete/Connect(...)` line in `internal/api/server.go` must have a corresponding `RoutesMetadata()` entry, and vice versa. The observability paths (`/metrics`, health) are the only exception — `addObservabilityPaths()` in `cmd/openapi-gen/main.go` injects those.
   - Run `go test ./internal/api/ -count=1`; the spec guard tests in `openapi_meta_test.go` catch tag drift.
   - Stage the regenerated `openapi.yaml` alongside the code change. Never leave the spec a commit behind the routes.

4. **Regenerate AsyncAPI spec** — If any VSI command (added, removed, renamed, payload changed) or any event in `internal/events` changed, update `internal/api/vsi_meta.go` (the `VSICommandsMetadata`, `EventsMetadata`, or `VSILifecycleFramesMetadata` registries) and run `make asyncapi` to regenerate `asyncapi.yaml`. Every VSI command and every event MUST appear in the registries — if it isn't there, it isn't in the spec. Never hand-edit `asyncapi.yaml` directly — it is generated by `cmd/asyncapi-gen/` and manual edits will be overwritten. Use `make specs` to regenerate both `openapi.yaml` and `asyncapi.yaml` in one shot.

5. **Update API documentation** — If any REST API endpoints, request bodies, response schemas, or webhook events changed, update `API.md`. Include usage examples.

6. **Update README.md** — If new configuration environment variables or features were added, update the relevant tables/sections in `README.md`.

7. **Update `voiceblender.env.example`** — If any environment variable was added, removed, renamed, or had its default changed in `internal/config/config.go`, update `voiceblender.env.example` in the repo root to match. Every env var the server reads must appear in the example file with its real default value; secrets/empty defaults are shown as empty assignments. The example file is committed; the actual `voiceblender.env` is not.

8. **Unit tests** — Every new feature, package, or extension to an existing package must have unit tests.

9. **Integration tests** — Every new or updated feature must have integration tests in `tests/integration/`.

10. **Update TESTING.md** — If new test commands, test files, test data setup steps, or testing workflows were added, update `TESTING.md` with the relevant instructions and test list entries.

11. **Do not change API unless required** - We should keep API unchanged as much as possible to keep backwards compatibility. 

## Git commits

Never run `git commit` (or any other git operation that creates a commit, including `git commit --amend`, `git merge --no-ff`, `git rebase`, etc.). Stage changes and leave the commit to the user. This applies even when work is finished and "ready to commit" — stop at staging.

## Code comments

Keep code comments minimal. Default to no comment. Only add one when the **why** is non-obvious — a hidden constraint, a subtle invariant, a workaround for a specific bug, behaviour that would surprise a reader. One short line is almost always enough; never write multi-paragraph rationale, narrative, or war-story comments inline. Don't restate what well-named code already shows. Don't reference specific vendor implementations, past incidents, ticket numbers, or "we used to do X, now we do Y" in source — that belongs in commit messages or PR descriptions.
